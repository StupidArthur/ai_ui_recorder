# 翻译链路修改方案与验收标准

日期：2026-09-12
状态：结构改造已实施；确定性测试已通过，真实模型语义质量验收待执行。

## 1. 目标与范围

本次改造以代码逻辑和输出结构调整为主，同时优化 Phase 1、Phase 2 提示词，交付可被下游 web-ui-case-debugger 消费的高质量“录制生成版”。

质量底线：现有 Phase 3 已正确表达的操作、目标、输入、按键、顺序和有效结果不得丢失；新增内容必须能追溯到录制证据或明确的执行配置。保留旧文件本身不能证明质量不回退。

范围限于 `translate_gui/` 及相关文档。录制端数据协议保持稳定。沿用现有 StructuredStep 和连续 CaseSlice，不引入通用插件框架、复杂 Case 依赖图或额外的 LLM 渲染阶段。仅在缺失信息确实需要跨阶段传递时增加少量字段。

## 2. 当前实现与需要解决的问题

下列路径均相对于 `translate_gui/`。

| 位置 | 当前行为 | 修改理由 |
|---|---|---|
| `internal/translator/phase3_agent.go` | 使用 Description 生成操作，仅针对 keyPress 补充 Key；AssertText 拼在同一行 | 结构化输入或目标可能未体现在描述中；操作和校验不易独立执行 |
| 同上 | 整体标题和目的取第一个切片，随后输出所有切片 | 多个 Case 的语义被第一个 Case 代表 |
| `internal/translator/phase2_slice.go` | 用 consume 重建区间；剩余为零时仍可能将 consume 重设为 1 并追加切片 | 必须阻止窗口耗尽后的多余切片，避免重复或无效范围 |
| 同上 | 覆盖报告使用布尔集合 | 能列出遗漏，但不能证明每步恰好覆盖一次；需要强校验 |
| `prompts/md/phase-2-slice-case.md` | 要求相邻区间编号加一连续；强调 2～6 步及最小原子目标 | 有效 ID 可能不连续；数量和连词规则可能导致过度切分 |
| `internal/translator/workflow.go` | Phase 1/2 部分写文件调用忽略错误；完成事件早于审计 Finalize | 中间产物或审计失败不应提前宣告完整成功 |
| `internal/translator/service.go`、`frontend/src/App.tsx` | 产物路径和展示逻辑依赖独立 Phase 4 | 三阶段改造需要同步更新读取、进度、默认预览和历史兼容 |

Phase 1 提示词的客观证据约束应保留；重点增强明确定位、准确输入和完成标准，避免泛化为“输入手机号”“URL 变化”而丢失已有的具体证据。

## 3. 目标流程与产物

```text
录制校验与证据预处理
  → Phase 1：生成并校验标准 Step
  → Phase 2：划分并校验连续 Case
  → Phase 3：确定性生成多种格式
```

校验作为阶段内普通函数，不增加用户可见的新阶段。Phase 3 不调用 LLM。

| 路径 | 用途 |
|---|---|
| `translate/phase3/agents.txt` | 兼容已有下游的 Agent 文本；保留既有语义并修正多 Case 标题表达 |
| `translate/phase3/runnable_case.md` | 默认产物，贴合 debugger 模板，明确标注“录制生成版” |
| `translate/phase3/cases.md` | 人类阅读表格，承接原 Phase 4 |

新翻译不再写 `phase4/`。历史数据仍允许读取 `translate/phase4/cases.md`，不批量迁移或删除旧文件。默认预览优先级：新 debugger Markdown → 新表格 → 历史表格 → agents.txt。界面支持切换已有格式，历史记录仅按实际存在的产物展示。

## 4. 分阶段修改

### 4.1 Phase 1：先保证事实完整，再改善描述

代码涉及：`preprocess*.go`、`prompt_builders.go`、`phase1_extract.go`、`workflow.go`，必要时调整 `internal/domain/models.go`。

1. 检查 action → enriched action → Prompt → StructuredStep 的字段传递，保留来源编号以及已有的角色、label、placeholder、区域上下文、输入值和按键。来源 ID 可以保存在结构化产物中，无须全部显示在正文。
2. 校验每条有效 enriched action 恰好得到一条 Step，拒绝重复和未知 ID；缺失项使用现有受控 fallback，明确记录原因。原始 action 经合并后的来源可追溯，不能把“N 进 N 出”错误套用到合并前的数据。
3. 结构化字段与自然语言描述不一致时，优先保留可验证的原始事实并标记冲突，不能让模型文本覆盖真实输入。缺少输入或定位依据时生成明确待确认项，避免输出“输入录制值”这类无法执行的指令。
4. 降级和待确认状态须随中间产物保存；仅有内存标记不足以支持重新渲染和评测。字段保持最小，不扩展成通用风险系统。

提示词涉及：`internal/translator/prompts/md/snapshots-2-steps-skill.md`。

- action：命令式描述，优先使用有证据的目标角色、名称及必要区域；已知输入值与完整按键必须明确。
- observation：保留录制观察事实；assertText：从事实提取可核验的完成标志。无变化不编造结果。
- 动态值按用途处理：用户输入、业务配置和明确要求核对的值保留；运行期指标通常校验展示。观察记录可以保留原值，不能将所有数字统一删除。
- 同名目标和动态名称只有在证据足以确定唯一目标时才生成区域或前缀定位；否则标记待确认，不自行选择“最新”“第一个”。
- XML 协议和一条输入对应一条 Step 的约束保持不变，任何新增标签必须同步更新解析器和契约测试。

### 4.2 Phase 2：保持简单切片，提高边界质量

代码涉及：`phase2_slice.go`、`phase2_helpers.go`、`workflow.go`。

1. 连续性以 effectiveSteps 的位置为准，支持 `[2, 5, 9]` 这种非连续 ID。consume 等于实际有效步骤数量，而非 endStep-startStep+1。
2. 空窗口安全返回；窗口耗尽即停止追加；对零消费、超额消费、非法范围和模型多余输出做有记录的校正或兜底。
3. 渲染前强校验：每个有效 Step 恰好属于一个切片，顺序不变，每个区间非空且 consume 与覆盖数相符。不能修复的错误终止流程，不能只写覆盖报告后继续。
4. 保持现有滑窗和有界 fallback，明确记录兜底切片。跨窗口尚未完成的业务段允许保留尾部待下一窗口处理，同时保证每轮推进；不引入新的规划 Agent。

提示词涉及：`internal/translator/prompts/md/phase-2-slice-case.md`。

- 以业务流程完整性决定边界；弹窗关闭、页面跳转是参考信号，不能一律视为 Case 结束。
- 去掉强制按连词拆分和固定短步数倾向；不因流程超过 8 步而机械拆分。
- Case 目的必须有步骤支持，不臆造测试覆盖或成功结论。
- 默认按录制顺序串行执行。Case 分组不意味着独立可运行；后续 Case 承接前面页面与数据状态，不凭空补充重置、登录或重复创建动作。

### 4.3 Phase 3：多格式输出与下游适配

代码涉及：`phase3_agent.go`、`phase3_human.go`、`run_layout.go`、`workflow.go`，新增普通 Markdown 渲染文件即可。

1. 将表格生成函数归入 Phase 3，统一编排三种格式，共享有效 Step 和 Case 分组。
2. Agent 文本保留原有步骤和有效断言；改进多 Case 标题与目的表达，不把第一个切片的目的当成整段录制的唯一目的。
3. debugger Markdown 遵循 H3 用例标题、H4 执行约定/步骤、粗体操作/预期标签、有序操作列表与预期复选框，不使用表格或 H1/H2。
4. 每个 Case 保留名称和目的，说明按录制顺序承接状态。起始 URL 属于整个流程的入口，不能暗示每个后续 Case 都应重新打开该 URL。
5. 操作与对应预期就近输出；中间会消失的弹窗、提示和状态在下一操作前检查，不能把所有检查移到 Case 末尾。没有可验证结果时说明未提取到可见结果，不填入虚构断言。
6. 有可靠完成标志时可输出等待；等待条件与预期分别承担执行推进和结果核对职责。超时或轮询参数来自明确的统一执行配置，标注为配置值；录制动作间隔不等于任务耗时上限。无可靠条件则列为待确认。
7. 未录到的弹窗分支、密码、canvas 等价操作不自动补齐。缺失值以明确参数或待确认项呈现；密码明文不写进产物，可引用用户执行时提供的凭据参数。
8. 信息缺失与降级通过“执行约定”中的待确认列表呈现，关联到具体步骤。标注“录制生成版”，不声称满足无人介入运行标准。

参考依据：`translate_gui/web-ui-case-debugger-skill/` 中的 `SKILL.md`、`rewrite.md`、`rules.md`、`runnable-template.md` 和 `completion.md`。本次使用其输出约束；实际调试轮次和最终可运行判定由下游负责。

### 4.4 工作流、界面与兼容

- 新流程只显示 Phase 1/2/3；Phase 3 显示“生成格式化产物”，可显示当前生成的格式。
- 路径常量、详情文件列表、默认预览及 Markdown 展示同步更新。
- 所有必需中间产物、三种最终产物和审计写入成功后才发送完成事件。失败返回具体文件与阶段，允许保留诊断文件，但不能显示本次完整成功。
- 同一 run 重新翻译失败时，旧产物不能被标记为本次成功结果；用最小的本次状态记录区分成功、失败和历史遗留输出，不设计完整版本管理系统。
- 保留用户自定义 Prompt。评测明确使用内置新版还是自定义版本；界面/说明应提示自定义 Prompt 不会自动获得新规则，不静默覆盖用户内容。
- 实施完成后同步更新 `doc/translate_design.md`、`doc/design.md`、`doc/run_directory_layout.md`、`doc/requirements.md`、`doc/user_manual.md` 和相关 README。本文为方案，当前不改写现状文档。

## 6. 验收标准

以下为本次拟采用的发布门槛，不是已取得的测试结果。

### 6.1 硬性门槛

| 编号 | 检查对象与方法 | 通过标准 |
|---|---|---|
| A01 | 固定 enriched action 集合与 Phase 1 Step ID 比对 | 有效输入恰好映射一次；未知/重复 ID 为 0；每个缺失项有明确失败或 fallback 记录 |
| A02 | 对标注样本比对动作、目标、非敏感输入、按键和先后顺序 | 关键事实保留率 100%；关键事实冲突为 0；敏感输入使用凭据引用，不以明文保留率衡量 |
| A03 | Step/Case 自动覆盖检查 | 有效步骤覆盖率 100%，重复覆盖为 0，乱序为 0，consume 正确；不成立时禁止进入渲染 |
| A04 | 空窗口、ID 间隔、零/超额消费、多余 slice、无效 XML、调用失败 | 不 panic、不死循环、不追加耗尽后的切片；受控兜底可追溯 |
| A05 | 同一 Step/Case 输入生成三种格式并按事实标注比对 | 三者动作、输入、按键、顺序及有效结果语义一致；格式差异不得丢信息 |
| A06 | debugger Markdown 结构检查与人工阅读 | 标题层级、操作/预期列表符合模板；全部标为录制生成版；中间检查不被后置 |
| A07 | 动态值、同名元素、缺少密码、canvas、未知等待场景 | 无证据的动作/输入/定位策略/断言新增数为 0；影响执行的已知缺口全部关联到步骤 |
| A08 | 模拟必需产物或审计写入失败、重新翻译失败 | 返回失败与具体原因；不发送成功完成事件；旧结果不冒充本次成功 |
| A09 | 新记录及仅有旧 agents.txt/旧 phase4 表格的历史记录 | 均能按实际存在文件预览；新记录默认显示 debugger Markdown；无独立 Phase 4 进度 |
| A10 | 自定义 Prompt 与内置 Prompt 场景 | 用户自定义内容未被覆盖；验收记录能确定实际使用的 Prompt |
| A11 | 对原始录制文件计算前后哈希 | `meta.json` 和 `record/` 内容完全不变 |

### 6.2 “质量不回退”的测量

建立至少 8 个固定场景，可来自同一录制的独立片段，但必须有逐步事实标注：登录及凭据缺失、输入与 Enter/快捷键、同名目标、动态名称与指标、短暂弹窗/提示、异步任务、跨 Case 状态依赖、噪声过滤导致 ID 间隔。另用合成夹具覆盖解析和写盘异常。真实录制样本必须脱敏。

每个样本标注：来源 action、必须保留的操作事实、可验证观察、允许的分组边界、预期待确认项。允许多个合理分组，不以旧版文本或唯一切分答案作为真值。

分两层比较：

1. **确定性比较**：固定 Step/Case，比较旧 agents.txt 与新三格式的语义事实清单。A02/A05 必须全部通过；断言措辞可以变化，但不能丢掉已正确表达的完成标准。
2. **端到端比较**：同一录制、同一模型/协议/参数分别使用基线与新版，每个场景各运行 3 次，保存所有结果，不只挑最好的一次。记录关键事实保留率、无依据新增数、定位充分性、合理切分比例、待确认项识别情况、fallback 数和耗时/token。

端到端门槛：A02/A07 的关键事实与无臆造要求每次均通过；按标注清单计算的定位充分性和合理切分比例，各场景三次平均不得低于基线。至少两个预先选定的已知薄弱场景出现可复核改善，才称为本次质量增强。若基线已满分，要求保持满分，并以新增兼容格式和更明确的缺口说明验收，不制造虚假提升。

fallback 和待确认数量不要求盲目下降：明确暴露原先隐藏的问题是合理变化，需逐项说明。总体高分不能抵消任何漏步、错输入、错按键或虚构操作。

没有真实样本、模型调用结果或人工事实标注时，只能声明“结构/单元验收通过，语义质量验收待完成”，不能声称已证明翻译质量不回退。

### 6.3 工程与交互验证

- `go test ./...` 通过，默认测试不访问外部模型。
- 前端 `npm run build` 通过；交付桌面版本时 `wails build` 通过。
- 桌面冒烟：选择录制 → 翻译 → 三阶段进度 → 默认 Markdown → 切换三格式 → 查看待确认项 → 打开历史记录 → 检查失败提示。
- Phase 3 额外模型调用数为 0。记录时间和 token 对比；若相对基线中位数增加超过 20%，需说明对应收益和原因，不把性能数据缺失当作已达标。
- 下游可解析全部新 Markdown，并正确区分操作、预期和待确认信息。能完成一次实际调试流转可作为附加证据；“零介入完整跑通”不作为录制生成版的强制门槛。
